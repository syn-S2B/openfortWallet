ONLI / CONCEPT TO IMPLEMENTATION

This is different from the ground up.

Onli is not crypto. Think of Onli as an intelligent file — a digital thing.

Crypto, by contrast, is a record on a public ledger: an entry in a blockchain that states who holds what. Control of that entry comes from a private key — the access credential, not the asset itself. Onli is not a ledger record stored in a chain of blocks. Onli is a thing, not a record.

This distinction is more than a difference in concept — it is a fundamental shift in how the system works. Records and things behave very differently, so before you build a bridge between them, it’s essential to understand that Onli does not work the way records work.

Onli keeps a record of events that have occurred to a thing, called an Oracle. A blockchain ledger, by contrast, records an event; the activity of moving a record is the record. A transfer on a chain is just an entry saying the claim moved. The activity is the record — there is no separate thing it is a record of.

Onli is different from the ground up. This is why our nomenclature is different.

Onli.Ai Works Differently Too

This is also why you need to adopt these concepts when you write for Onli.Ai. You don’t let an AI generate behavior and hope it’s right. You build a Tool first — an atomic piece of code that does one bounded thing, under one explicit contract, proven before anything depends on it. You then compose proven Tools into Workflows — reusable responsibilities that select only what the current context requires — and compose Workflows into Journeys that own one caller-visible outcome. You classify from the outcome downward and build from the atomic layer upward, so a large product surface rests on a small, proven core.

Because everything the AI can do already exists as a proven Journey, Workflow, and Tool, the AI’s only job is to decipher intent and call the right unit. It cannot hallucinate a capability that was never built, improvise a step that was never tested, or accidentally do something the user didn’t want — there is no path for that to happen. The user says they want to send funds; the AI recognizes the intent and calls journey_send_funds, which executes only steps that were built once, contract-tested, and reused everywhere above them. The intelligence is in the intent. The execution is in the proven architecture.

The concepts

Onli uses five concepts. Each has one clear job.

  • Journey: owns one outcome the user wants, such as sending funds. It coordinates the work and handles completion or recovery.
  • Workflow: owns a reusable part of that work. It selects the Tools and other Workflows the current situation needs.
  • Tool: performs one bounded operation under a clear, tested contract, such as checking a destination.
  • Recipe: defines the arrangement, conditions and settings for the work. Provider selection belongs here: the Recipe chooses the approved provider binding. It does not execute anything.
  • Resource: is what the work uses, changes or produces, such as a wallet, transfer request or receipt. Its identity says what it is; its content holds its data; its context describes the situation.

Start with the outcome and break it into reusable work. Build and prove the Tools first, then compose the Workflows and Journey.

Connecting a provider

A Capability is a Tool that offers a stable operation independent of the provider. It defines the inputs, permissions, results and evidence needed to call the work complete.

An Adapter translates that contract into the provider’s API and translates the response back. Only the Capability calls its Adapter; the Workflow stays independent of the provider.

Journey → Workflow → Capability → Adapter → Provider

For a send, the Journey owns the outcome, Workflows prepare and execute it, and Tools check the request and evidence. The Recipe selects approved settings. The Resources hold the wallet, request and result.

What you need to build

Use sending funds as the first complete example. Build the small operations, compose them into reusable Workflows, then expose a Journey that owns the result. Reuse an existing unit when its contract fits.

The Workflows

  • workflow_prepare_transfer: validate intent, read balances and estimate the exact transfer.
  • workflow_review_transfer: check the selected destination and unresolved-operation guard, then reuse preparation.
  • workflow_recover_wallet_session: obtain fresh access, recover and verify the wallet, perform a scoped action and clean up. Send and export reuse it.
  • workflow_execute_transfer: verify confirmation, reuse wallet recovery, check current balances and submit.
  • workflow_reconcile_transfer: observe the original operation, verify evidence and update its result.

Here is a complete small Workflow using the existing preparation Workflow. Types and signatures come from this repository; the caller supplies the selected wallet and transfer fields.

import { workflow_prepare_transfer } from './workflow_prepare_transfer.ts'
import type { Wallet } from '../contracts/species.ts'
import type { Asset } from '../contracts/wallet.ts'

export async function workflow_quote_transfer(input: {
  wallet: Wallet
  asset: Asset
  recipient: string
  amount: string
}) {
  return workflow_prepare_transfer(
    input.wallet, input.asset, input.recipient, input.amount,
  )
}

This example shows reuse rather than another implementation of validation, balance reads and fees. In the full application, use workflow_review_transfer so destination selection and continuity guards are also checked.

The Journey

journey_send_funds is the conceptual outcome. This client names its implementation journey_send_transfer. Review happens first; explicit confirmation continues that intent into the Journey. A returned hash is pending. Reconciliation supplies completion evidence later.

The following composition uses the actual client API. The application supplies the signed-in session, selected wallet, reviewed quote, owner/wallet-scoped storage key and context callbacks. confirmation is created only in the explicit user-confirmation handler.

import { journey_send_transfer } from '../journey/journey_send_transfer.ts'
import { workflow_execute_transfer } from '../workflow/workflow_execute_transfer.ts'
import { createTransferConfirmation } from '../contracts/transfer-confirmation.ts'

// Inside the user's explicit Confirm handler:
const confirmation = createTransferConfirmation(quote)
const result = await journey_send_transfer({
  session,
  wallet,
  quote,
  confirmation,
  key: operationStorageKey,
  storage: localStorage,
  isCurrent: () => currentSessionAndWalletStillMatch(),
  send: workflow_execute_transfer,
  changed: record => showOperation(record),
})

showOutcome(result)

The Journey locks the operation, checks for an existing unresolved intent and persists the operation before broadcast. It never automatically repeats a broadcast after a lost response. Callers display pending or indeterminate honestly and continue observation of that same operation.

What you write as the provider

Your main implementation is the Adapter. It translates the agreed Capability operation into your SDK or API and translates the result back. You also supply its versioned Recipe binding and contract tests. You reuse the existing Journey, Workflows and pure Tools wherever their contracts fit.

  1. Agree the contract. Define the wallet identity, required permission, supported operations, result states and completion evidence. State any unsupported custody, export or network behavior.
  2. Write the private Adapter. Initialize your provider, recover the exact issued account, perform the approved operation and clean up. Translate errors without exposing credentials or raw provider responses.
  3. Register it through the Capability. Add the implementation to the Capability’s private Adapter selection. Workflows call the Capability; they never import your SDK.
  4. Supply a Recipe. Select the approved Adapter version and permitted network/timing settings. Preserve that binding on each operation.
  5. Prove it. Test identity mismatch, missing approval, cancellation, cleanup, lost responses and repeated operation IDs before integrating it into the Journey.

This is the existing minimal recovery contract. It illustrates what a provider session must return; send and export require their additional contracts.

type WalletSDK = {
  waitForInitialization(): Promise<unknown>
  recover(account: string, encryptionSession: string): Promise<{
    id: string
    address: string
    chainId?: number
    accountType?: string
  }>
  logout(exportCompleted: boolean): Promise<unknown>
}

Use src/adapter/adapter_openfort.ts as the implementation reference. The encryptionSession handoff here is Openfort/Shield-specific. A different provider needs an agreed access contract with the Capability and backend; do not put an unrelated credential into that field.

How your work fits

User intent and explicit confirmation
  → Journey owns the send outcome
    → Workflows prepare, execute and reconcile
      → shared Tools check intent, identity and evidence
      → Capability owns the provider-independent contract
        → your Adapter translates to your wallet provider

Recipe selects the approved provider and settings.
Resources preserve the wallet, intent, operation and evidence.

The provider backend supplies account provisioning and permitted temporary access. Service secrets stay server-side. An access handoff is not transfer approval. See docs/GATEWAY_CONTRACT.md for this client’s Species integration contract.

Completion needs matching evidence. This client verifies current transaction inclusion, including the exact USDC event where relevant; it does not promise irreversible finality. A timeout after possible broadcast remains unresolved. Keep the original identity and binding and recover it instead of sending again.

If the bridge also changes an Onli thing, agree the Onli-side operation and Oracle event contract separately. This client supplies no Oracle-writing endpoint. A blockchain receipt proves neither that the Onli-side effect occurred nor that its Oracle was updated.

Encryption is part of the contract

In transit: use authenticated, encrypted connections between the client, Onli and your provider. Validate certificates and authenticate the caller. Where the Capability requires an encrypted message envelope, preserve its format and integrity checks; encryption does not replace permission checks.

At rest: encrypt sensitive persisted data, including wallet key material, backups, credentials and protected operation data. Keep encryption keys separate from the data, restrict access and define key rotation and recovery. Never persist plaintext private keys or session secrets in browser storage or logs.

Your Adapter must meet both requirements and document who owns the keys at each boundary. Use the agreed cryptographic formats and tested libraries; do not invent a new encryption scheme.

In this implementation, the Species proxy uses authenticated AES-256-GCM message envelopes and encrypted backup files use the existing canonical format. The proxy permits loopback HTTP for local development; production connections require HTTPS. Browser continuity records contain operation metadata and are currently stored without application-level encryption. They contain no plaintext private keys or session tokens, but encrypted storage for protected metadata and provider-side encryption at rest must be established and verified for a production integration.

Your deliverables

Provide the Adapter, approved Recipe binding, identity/permission mapping, recovery rules, encryption and key-management evidence, and passing contract tests. Include backend requirements and evidence from real provider testing. The reusable send architecture then calls your implementation through the Capability.
