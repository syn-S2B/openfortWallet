IMPLEMENTATION / CODE WALKTHROUGH

How we built the Openfort wallet.

Use the Openfort wallet we built as a working example for your Onli Appliance. Follow one send outcome through its Recipe, Tools, Workflows and Journey.

These excerpts show how the wallet implementation fits together. They are selected excerpts, not standalone programs. Each source path identifies where the complete code lives.

Start with the send example and the authentication sequence. Here you will trace that same request through the implementation. A Surface means the user interface; a binding is the selected version; continuity is the saved operation state used after an interruption.

1. Select Openfort with the Recipe

Provider selection is a Recipe responsibility. The versioned definition selects openfort/v1 for the recovered-wallet-session Capability. It contains no execution or secret values. The external Openfort service is reached through the selected Adapter.

The separate wallet-network/v1 Recipe defines mainnet/Sepolia RPC, token and explorer settings. wallet-polling/v1 holds observation intervals and quote lifetime. The transfer records its selected bindings before any effect; recovery cannot silently substitute another selection.

2. Define the Resources and contracts

The wallet’s identity comes from Species. The client verifies the account reference, address, custody/type and any reported chain. A transfer Resource preserves operation identity, exact intent, bindings, hash and evidence. A quote contains the exact transaction and its fee/time limits.

The session interface names the operations Workflows need. It exposes no raw provider handle. Openfort implements this interface privately.

src/contracts/wallet-session.ts

The confirmation Tool verifies the reviewed wallet, chain, quote time and exact transaction. Reusing this check at the effect boundary prevents a valid review from authorizing an edited payload.

src/tool/tool_verify_transfer_confirmation.ts

export function tool_verify_transfer_confirmation(
  wallet: Wallet,
  quote: Quote,
  confirmation: TransferConfirmation | undefined,
  now = Date.now(),
) {
  assertQuote(wallet, quote, now)
  if (
    !confirmation ||
    confirmation.kind !== 'explicit_transfer_confirmation' ||
    !confirmation.operationId ||
    confirmation.walletAddress.toLowerCase() !== wallet.address.toLowerCase() ||
    confirmation.chainId !== wallet.chain_id ||
    confirmation.quoteCreatedAt !== quote.createdAt ||
    !Number.isFinite(confirmation.confirmedAt) ||
    confirmation.confirmedAt < quote.createdAt ||
    confirmation.confirmedAt > now ||
    JSON.stringify(confirmation.transaction) !== JSON.stringify(quote.transaction)
  )
    throw new WalletError('Explicit confirmation of this exact transfer is required.')
}

4. Compose reusable Workflows

Review selects the destination and checks existing unresolved work. Preparation validates intent, reads balances through the chain Capability and estimates an immutable transaction. Recovery owns the complete access-renewal, initialize, recover, identity-check, action and teardown lifecycle.

Execution composes recovery with send-specific checks. It does not import Openfort or obtain a raw provider. withWalletSDK is the wallet-session Capability entry point; runWalletAction aliases the shared recovery Workflow.

src/workflow/workflow_execute_transfer.ts

export async function workflow_execute_transfer(
  session: Session,
  wallet: Wallet,
  quote: Quote,
  isCurrent: () => boolean,
  broadcastStarted: () => void,
  confirmation: TransferConfirmation,
) {
  tool_verify_transfer_confirmation(wallet, quote, confirmation)
  return withWalletSDK((createSDK) =>
    runWalletAction({
      wallet,
      isCurrent,
      createSDK,
      getAccess: () => readWalletAccess(session),
      async action(sdk, check) {
        const balance = await readBalances(wallet)
        check()
        assertQuote(wallet, quote)
        if (
          balance.eth < quote.fee + (quote.asset === 'ETH' ? quote.units : 0n) ||
          (quote.asset === 'USDC' && balance.usdc < quote.units)
        )
          throw new WalletError('Your balance changed. Review the transfer again.')
        return sdk.sendTransfer(wallet, quote, check, broadcastStarted, confirmation)
      },
    }),
  )
}

Member backup export reuses the same recovery lifecycle through workflow_export_wallet_key. We built recovery once, rather than separate Openfort login/recovery implementations for send and export. Context controls the scoped action.

5. Connect the Capability to the Adapter

The Capability resolves the Recipe’s Adapter binding, owns coordination across browser tabs on the same site and returns only canonical scoped operations. The provider registry is private to this owner.

src/capability/tool_capability_wallet_session.ts

export function createWalletSessionCapability(recipe: WalletProviderRecipe = walletProviderRecipe) {
  const adapters = { 'openfort/v1': adapter_openfort_factory }
  const selected = adapters[recipe.adapter]
  if (!selected || recipe.version !== 'wallet-provider/v1' || recipe.capability !== 'recovered-wallet-session/v1')
    throw new WalletOperationUnavailable('The selected wallet provider binding is unavailable.')

The Adapter alone imports the Openfort SDK and translates the canonical recovery call into its automatic recovery API. Its storage is isolated per operation; the access token callback renews only the permitted handoff.

src/adapter/adapter_openfort.ts

export async function adapter_openfort_factory(cleanup: WalletCleanupGuard): Promise<WalletSessionFactory> {
  const { Openfort, RecoveryMethod, ThirdPartyOAuthProvider } = await import('@openfort/openfort-js')
  return (access: WalletAccess, getAccessToken: () => Promise<string>) => {
    const storage = new WalletSessionStorage()
    const sdk = new Openfort({
      baseConfiguration: { publishableKey: access.publishable_key },
      shieldConfiguration: { shieldPublishableKey: access.shield_publishable_key },
      thirdPartyAuth: { provider: ThirdPartyOAuthProvider.CUSTOM, getAccessToken },
      overrides: { storage },
    })
    return {
      waitForInitialization: () => sdk.waitForInitialization(),
      recover: (account: string, encryptionSession: string) =>
        sdk.embeddedWallet.recover({
          account,
          recoveryParams: { recoveryMethod: RecoveryMethod.AUTOMATIC, encryptionSession },

The excerpt ends before export, send and logout methods. Send obtains the raw Ethereum provider privately, then calls the EVM submission Adapter. Its checks run again immediately before the effect.

src/adapter/adapter_evm_submit.ts

check()
  tool_verify_transfer_confirmation(wallet, quote, confirmation)
  assertQuote(wallet, quote)
  const [chain, accounts] = await Promise.all([
    provider.request({ method: 'eth_chainId' }),
    provider.request({ method: 'eth_accounts' }),
  ])
  check()
  tool_verify_transfer_confirmation(wallet, quote, confirmation)
  assertQuote(wallet, quote)
  if (
    typeof chain !== 'string' ||
    BigInt(chain) !== BigInt(wallet.chain_id) ||
    !Array.isArray(accounts) ||
    accounts.length !== 1 ||
    String(accounts[0]).toLowerCase() !== wallet.address.toLowerCase()
  )
    throw new WalletError('Signing wallet or network changed. Review the transfer again.')
  // After this point an error may mean broadcast succeeded. Never automatically retry.
  broadcastStarted()
  const hash = await provider.request({ method: 'eth_sendTransaction', params: [quote.transaction] })
  if (typeof hash !== 'string' || !/^0x[\da-fA-F]{64}$/.test(hash)) throw new Error('Unknown transaction outcome')
  return hash
}

broadcastStarted() persists continuity through the Journey’s callback. If that write fails, eth_sendTransaction is never called. Once it starts, an exception can mean the effect happened; uncertainty is preserved.

Logout and isolated storage disposal happen before releasing the origin lock. Failed cleanup activates a reload guard. This prevents a retained SDK session from starting another protected action after its scope ends.

The catch branch returns indeterminate after the broadcast boundary. It retains the pre-broadcast record and any known hash. It does not erase the guard or automatically submit a second transaction.

7. Establish the outcome

A hash is acknowledgment, not completion. workflow_reconcile_transfer calls the observation Capability. That Capability checks the original Recipe/RPC/token/wallet binding, reads the transaction and receipt, then invokes the evidence Tool.

The Tool checks hash, sender, target, input, value, chain, matching block and receipt status. USDC additionally needs the exact token Transfer event, recipient and units. A valid failed receipt establishes failure; unavailable observations leave the operation unresolved.

src/workflow/workflow_reconcile_transfer.ts

const next: Submission = {
      ...saved,
      hash: options.operation.hash,
      status: result.status,
      state: result.status === 'confirmed' ? 'completed' : 'failed',
      duty: undefined,
      evidence: [...(saved.evidence ?? []), ...result.evidence],
    }
    options.storage.setItem(options.key, JSON.stringify(next))
    return next
  })
}

Our declared completion contract is transfer-inclusion/v1: matching current inclusion. It does not claim irreversible finality, an Onli-side change or an Oracle update. Those need their own contracts and proof.
